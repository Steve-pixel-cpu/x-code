## x-code 上下文压缩修复计划（最终版）

诊断：①压缩触发把"本轮多次 API 调用的 usage 累加和"当成"当前上下文体积"（`runtime.py:581` 读 `current_turn_usage()` 累加器），真实上下文 15~20k 时迭代几次即误触发；②阈值 100k 按 128k 窗口标定，GLM-5.3-Flash 实际 1M 窗口；③误触发后粘性永不复位 + 摘要极度有损（工具结果 40 字符），模型失忆→反复重读→无尽短思考。

### Fix 1（核心）：修正压缩触发口径
- `runtime.py` `UsageTracker`：`record()` 保存最近一次单调用 usage（`self._last_call = usage`，替换非累加），新增 `latest_call_usage()`
- `_context_over_compact_threshold()`（runtime.py:581）改读 `latest_call_usage().context_tokens()`；输出预算检查（runtime.py:614）保持累加口径不变
- 同步修正 `_maybe_auto_compact` 注释，使文档与实现一致

### Fix 2：阈值按 1M 窗口校准 + 窗口可配置
- `config.py`：新增 `context_window` 配置（键 `contextWindow`、env `CLAUDE_CONTEXT_WINDOW`），默认 1_000_000
- `token_budget` 语义改为：未显式配置时 = `context_window × 0.75`（即默认 750_000）；显式配置/`CLAUDE_TOKEN_BUDGET` 仍覆盖。`main.py` 接线不变
- 注释注明：第三方中转窗口缩水时用 `contextWindow` 调小

### Fix 3：LLM 摘要（一步到位），规则摘要降级为 fallback
- `runtime.py` 新增 `_llm_summarize(msgs)`：压缩激活后首次构建视图时，用 `api_client.stream()` 发起一次 side-call——messages = 被压缩历史原样（API 格式，1M 窗口装得下 ≤750k 历史）+ 末尾一条 user 摘要指令；thinking 用 `low` 档控制耗时
- 摘要指令（放 `compact.py`）：要求结构化输出——用户主请求与意图、关键技术上下文、涉及文件与关键位置（file:line）、已做修改、错误与修复、已确认的事实结论、待办与下一步；强调保留具体事实（路径/行号/命令/错误原文），禁止泛泛而谈
- 安全约束：side-call 不进会话历史、usage 不 record 进 turn 累加器（不干扰预算检查）、不会递归触发压缩（`_maybe_auto_compact` 只在 run_turn 循环内调用）
- fallback：side-call 任何异常/超时/空返回 → 回退现有 `summarize_messages()` 规则摘要；同时修正其自相矛盾提示语（"do NOT re-read their sources" → "工具原始输出已归档，如需精确内容请重新读取"），其余规则摘要逻辑不动
- 缓存：复用 `_compact_cache`（切割点, 摘要）机制，LLM 摘要生成一次后按切割点缓存
- `continuation_message` 前缀不变，前端压缩提示卡（app.js 固定前缀识别）无需改动

### Fix 4：单轮输出预算放宽
- `DEFAULT_TURN_OUTPUT_BUDGET` 131_072 → 262_144（容纳 ~16 次大思考调用），config `turn_token_budget` 默认值同步

### 明确不做
- 粘性标记保留（压缩视图生效后 usage 骤降，解除即振荡，粘性是防振荡必需）
- 摘要不做配置开关（按你的选择，LLM 摘要即唯一主路径，规则摘要仅作故障 fallback）
- thinking 入史不动（非主因）

### 测试与验证
- `tests/test_auto_compact_signal.py` 新增回归钉：单轮 8 次迭代、每次 usage 15k（累计 120k）不误触发压缩
- 新增 LLM 摘要测试（mock api_client）：正常路径（LLM 文本成为摘要并缓存）、异常路径（fallback 规则摘要）、缓存复用
- 全量跑现有测试；手动验证：临时调小阈值跑多工具迭代会话确认不再误触发，`/compact` 验证 LLM 摘要质量与 fallback
